## Decisions

A market simulator's product is trust, and trust lives in the choices that had no single right answer. How realized PnL books when a position flips through zero, whether a spot account can short, when funding is charged relative to liquidation inside one bar: each could reasonably go more than one way, and once chosen it has to hold consistent across the whole engine. This page records those choices and the reasoning behind them, so a reader can check why a behavior is the way it is, and a contributor does not quietly undo a deliberate choice while fixing what looks odd.

Every decision keeps a number. The code and the other guides cite them by that number (`ADR 0017`), so the number is the stable handle even as the wording here is tidied.

<br>

## The Shape of the Library

The library is a stack of layers, and the one rule is that logic flows up, never sideways: each layer builds only on the one below it.

- **`emsl-core`** is pure primitives: the units, the OHLCV bar, the order and fill types, the netted position, the account (equity, funding, liquidation, realized and unrealized PnL), the cost model, and the resting-order book. It knows nothing about a candle *series*, parallelism, or Python: it holds one bar, never the time series, the windows over it, or any bar-level fill logic, all of which live in `bar-engine`. This is the seam a future tick or L2 engine would reuse.
- **`bar-engine`** is the bar-level realization: the candle series, the next-bar fill model, the single `step()` machine, the reporter and its stats, and the parallel batch and sweep. It builds only on `emsl-core`.
- **`emsl-py`** is the one crate that links Python. It parses arguments, copies candles once from numpy, hands state back as dicts, vends the zero-copy observation, and releases the GIL around the batched step. It holds no simulation logic.
- **`python/emsl`** is everything that is not simulation, and it has two halves. The drivers wrap the engine's loop or orchestrate many runs of it: `backtest`, `rl`, `tune` and `walk_forward`, with `Market` carrying the eleven engine knobs once so that no two of them can drift apart (ADR 0053). This is what "one engine, many surfaces" means in practice: a backtest, a Gymnasium RL env and a parameter search are not three engines, they are ways to drive the same one, and a driver only configures the engine, drives its loop, and shapes the result. The other half never produces a run, it reads one: `metrics` evaluates a finished result, `ta` is functions of arrays that never see the engine, and `chart` draws. That half is the larger of the two by line count, and keeping the line between them sharp is what makes a defect there a wrong number about a correct run rather than a wrong run. Keeping the drivers thin is what keeps the core embeddable: it never assumes it is being used for a backtest rather than an RL rollout, so it drops into a system you already have instead of owning your loop.

**The tools that check the library are not the library (0084).** `dev/` holds what the wheel must never carry: the second simulator and the harnesses that drive it (`dev/differential/`), the generator behind every chart image in the documentation (`dev/charts/`), the mermaid sources behind the hand-made diagrams (`dev/diagrams/`), and `dev/golden.py`, which rewrites the chart spec's key-path golden. Nothing there is packaged, nothing under `python/emsl` imports it, and only the differential runs in the gate. What separates it from `tests/` is that a test asserts and a tool produces: the gate runs a test and fails a build, while a tool here is run by a person and writes a file that is then read and committed. The second simulator is the case that makes the line worth drawing, because filing the library's one independent reading among the tests written against the implementation is the single thing it exists not to be. Their documentation lives in the `.Documentation` set rather than beside them, for the reason the Contributor Guide already gives for every other folder: a reader who finds the directory before the guide learns half the story, and the half missing is always the why. That rule had been written down and not held. `dev/diagrams` carried its own README for as long as it existed, and no page named `golden.py` at all, so the one tool that has to be run in the same commit as the change it records was the one tool nobody could find. A test now enumerates the directory and fails if a tool appears that no page names, or if a README appears beside the code, because a convention held by review alone is a convention that rots quietly.

## Orders and Fills

**Flip-through-zero PnL (0001).** A fill that crosses zero splits in two: it closes the old side, booking realized PnL on that part at the old average entry, then opens the remainder fresh at the fill price. A same-side add volume-weights the entry, and a non-finite or non-positive size fills nothing.

**Slippage (0004).** A market (taker) fill slips by `slippage_bps` off the next bar's open, adverse to the side.

**Volume cap (0005).** One order takes at most `max_fill_fraction` of a bar's volume, so a large limit fills over several bars rather than all at once.

**Market impact (0013, extended by 0074).** An extra adverse slip proportional to the fraction of the bar's volume the fill takes, so a bigger order pays more. A per-fill cost function is deliberately refused; this coefficient is its fast-path stand-in.

**Time in force (0016).** `GTC` rests, `IOC` takes one bar then cancels the rest, `FOK` fills the whole size against one bar or nothing. A market order is `IOC` unless `FOK` is asked for, since it never rests and so cannot tell `GTC` from `IOC`; a stop rests until it triggers, then fills as a market order. The one-bar rule is why an unfilled market order is cancelled rather than carried: on a bar that trades no volume it fills nothing and is gone, exactly as an `IOC` limit would be, while a `GTC` limit waits for the next bar.

**A stop that cannot fill has not triggered (0035, extended by 0068).** The sentence above, read alone, says a stop becomes a market order the moment its trigger is crossed, and a market order that fills nothing is cancelled. That reading would delete a stop-loss on any bar whose volume is zero: the trigger is crossed, no liquidity exists, and the protection is gone with nothing to show for it. Three independent readers of this page reached exactly that conclusion, so the wording earned the correction. The engine binds triggering to filling instead: a stop is consumed only when it produces a fill, so on a bar that trades nothing it stays armed and protects the position on the next bar that can actually trade. The cost is that a stop can fire later than a live venue would have filled it, which is the honest direction for the error to run on illiquid data, and the alternative loses the protection silently. This is where the bar tier's fidelity limit (ADR 0006) shows most plainly.

**Moving a resting order (0032, extended by 0069).** `replace(id, ...)` cancels a resting order and rests a replacement carrying its side, kind and flags. It returns `None` and places NOTHING when the id is no longer resting, and that is the whole point: re-placing a trailing stop with `stop()` each bar rests a new order every time, so the one that fills leaves its siblings live and on a perp they open a position on the other side. A trail written with `replace` cannot leave two orders alive, and once its stop has filled the next replacement quietly does nothing rather than arming a fresh one. There is still no OCO group; `replace` covers the case that kept costing people real answers.

**Order status is not modelled (0033).** An order's lifecycle state was a field on the order and an enum with three variants, but nothing ever wrote it after construction, so `Filled` and `Canceled` were unconstructible and the field was the constant `Resting`. Only resting orders are ever exposed, since a filled or cancelled one is removed from the book, so the state carried no information. The field and the enum are gone; the `status` key stays in the order dict, documented as the constant it always was.

**Protective stops and stable order ids (0028).** `stop()` takes `reduce_only`, because the shortcut's whole purpose is a stop-loss and without the flag a stop that outlives the one that closed the position opens a fresh position on the other side. Nothing links resting orders: there is no OCO and no replace, so re-placing a trailing stop each bar rests a new order every time and, once the book is full, every further placement is rejected and the trail keeps only its oldest triggers. Cancel before re-placing. Order ids are unique for the engine's life rather than per episode; restarting the counter on reset meant a handle carried across one addressed a live order belonging to the next episode.

**Spot buys clamp to cash (0018).** A spot buy fills only what the quote balance affords, so a buy never drives the account negative.

**Spot cannot short (0015).** On spot a sell is clamped to the current long; shorting base needs a borrow this tier does not model, so a short and a flip through zero are perp behaviors.

**Bar-fidelity limits (0006).** At bar granularity the fill model cannot see the path inside a bar, so it can be slightly more generous than a live book, and two contradictory resting orders can both fill on one wide bar. These approximations are named rather than hidden. Resting orders resolve in book-slot order, and a cancelled slot is reused by the next placement, so when two orders fill on the same bar and a cash or margin clamp binds on the first one applied, which of them gets the room depends on slot order rather than on placement time. The one case where that mattered most, two exits from the same position, is settled by ADR 0056 instead.

**The cap and the slip are bounded (0024, extended by 0074).** The volume cap is a `min` against `max_fill_fraction * volume`, and `f64::min` keeps the other operand when one side is NaN, so both sides carry the guard: a non-finite remaining cannot launder a NaN size into a full-cap fill, and a non-finite fraction cannot delete the cap and let one order take more than the bar traded. Slippage and market impact are adverse by definition, so both are floored at zero, and their total is held just under 1: a slip of 1.0 would price a sell at zero and anything beyond it below zero, which is not a trade.

**All-or-nothing is decided after the clamps (0025).** `FOK` means the whole size fills or none of it, and the size that can actually fill is not the one the fill model offers: the perp margin cap, the spot cash and short clamps, and `reduce_only` all shrink it afterwards. So the decision is made against a clamped copy of the fill, and a `FOK` that could only fill in part books nothing. A resting `FOK` limit is judged against the account as it stands when its turn comes, not against a snapshot taken before the bar's earlier fills.

## The Input Boundary

**The boundary validates its arguments (0027, extended by 0070).** The candle array was checked for non-finite values from the start, on the reasoning that one would poison every mark downstream. Every other argument crossing into the engine now gets the same treatment, because they poison the same things: a NaN `quote` makes every state field NaN, a NaN `max_fill_fraction` deletes the volume cap, a fee at or below -1 turns the spot cash clamp's `1 + rate` divisor non-positive and mints equity, a negative `slippage_bps` fills better than the market, an unbounded `max_open_orders` allocates its slots up front and aborts the process rather than raising, and a zero observation `window` reaches Rayon's chunker and surfaces as a `PanicException`, which is not an `Exception` and escapes an ordinary `except`. A non-finite limit price or stop trigger is refused a book slot for the same reason a non-finite size is (ADR 0001): every comparison against it is false, so it can never fill and never expire, and it holds a slot until the book is full and later orders are silently rejected. Errors name the argument and the expectation.

## Accounting and Risk

**Funding (0002, 0017).** A perp charges funding on the held notional: a long pays a positive rate, a short receives. The cadence is measured in bars (`funding_rate`, `funding_interval`), anchored to the absolute bar index, and charged before the liquidation check, so a funding debit can bust the account on the same bar.

**Liquidation (0003, amended by 0052).** A perp is force-closed when its margin is exhausted. The trigger is tested at the bar's adverse extreme, the low for a long and the high for a short, so a wick that takes equity to zero kills the position even if the bar closes back above it. The close itself is priced at the point the margin runs out, not at that extreme; see ADR 0052 for why.

**Cash moves only with the position (0023).** The netted position ignores a fill that is non-finite or sized at or below its dust epsilon, and the account gates its cash move and its fee on the same test. They used to disagree: the account moved quote for a fill the position had already refused, so a sub-dust trade shifted cash with the position frozen, and a fee rate below -1 drove the spot cash clamp to a negative size that credited the account without trading. Quote cannot change unless the position changes with it. The sizing helpers follow the same rule and return zero rather than an infinity when the mark is not finite and positive.

**Leverage cap (0012).** `leverage` caps a perp's notional at that multiple of equity; the shipped default is a finite 10x, and `0.0` opts out into uncapped notional. Spot ignores it. A position already over the cap because equity fell is not force-reduced, only blocked from growing.

**An insolvent perp may only shrink (0026).** The margin cap used to switch itself off once equity reached zero, on the grounds that liquidation would handle it. Liquidation cannot handle it: it force-closes a position, and an account that is flat has none, so a fill opened from negative equity was admitted uncapped and then closed at the bar's adverse extreme, deepening the bad debt instead of being refused. With no equity there is no notional to back, so the allowance is zero and the only fills that pass are those that reduce.

**A non-positive equity is terminal (0019).** Equity at or below zero ends the account for both markets; the RL env reads it as a termination, not a truncation.

**Statistics (0007).** The stats set (return, CAGR, Sharpe, Sortino, Calmar, drawdown, volatility, and the trade metrics) with fixed conventions: sample deviation for the volatility and the Sharpe denominator, the population divisor on Sortino's downside deviation as that ratio is conventionally defined, square-root annualization, and a degenerate or busted run returns finite numbers rather than `NaN`, so a bad run cannot poison a sweep's argmax. `avg_trade_pct` is measured against starting equity, so a trade taken in a drawn-down account counts for its nominal size rather than the smaller one it really had.

**Statistics stay finite, monotone, and net (0029, extended by 0072).** Three ways the set could still mislead, closed. A `periods_per_year` of zero made the per-period risk-free rate `0.0 / 0.0` and handed back a `NaN` Sharpe, the one thing ADR 0007 exists to prevent, so a non-positive or non-finite annualization now falls back to none at all rather than propagating. Drawdown is capped at 100%: bad debt takes equity below zero, and an uncapped drawdown gave the deeper bust the larger divisor and therefore the higher Calmar, ranking it above a shallower one. And the trade metrics are computed net of the fee each row already records, because on gross PnL a strategy whose edge is smaller than its costs reported a perfect win rate and an infinite profit factor beside a negative total return.

**A trade carries its whole round trip (0030).** A trade row used to carry the closing fill's fee only, on the reasoning that the entry fee had already been charged to cash. That left roughly half the cost attributed to nothing, so the metrics built on it stayed optimistic even after ADR 0029 netted them: on one run the exit fees came to 31.60 and the unattributed entry fees to 31.63. The engine now tracks the fee paid to open the position it holds, and a close consumes the share belonging to the size it closes, so `fees` is the entry and exit sides together and `net_pnl` is `pnl - fees`. The identity that buys: on a run that ends flat with no liquidation, the net PnL of the logged trades equals the change in equity, which is asserted by a test.

**A run that never filled is visible (0031).** A series with no volume fills nothing, correctly and silently (ADR 0016), and the result was indistinguishable from a strategy that never placed an order: zero exposure, zero return, zero trades, and a full equity curve. `num_fills` counts the fills applied, so zero beside orders you know you placed says the feed is dead rather than the strategy quiet.

**A search needs a floor on activity (0034).** `tune` ranks on a point estimate, and a point estimate is best exactly where the sample is thinnest, so an unconstrained search walks to the cell with a handful of trades and the widest interval. `min_trades` fails a trial that closed fewer than that, the same treatment a `NaN` objective gets. It defaults to zero, so nothing changes unless asked for.

**Trade recording (0009).** One trade row per closed portion of a position, with `pnl` gross of fees, `fees` the whole round trip on that size (ADR 0030), and `net_pnl` the difference. A position still open when the data ends is never closed, so it appears in `total_return_pct` and `exposure_pct`, which mark it, and in none of the trade metrics, which count only completed round trips. Buy and hold therefore reports a real return beside zero trades; read `exposure_pct > 0` with `num_trades == 0` as "still open", not as "never traded".

## The Parallel and RL Tier

**Zero-copy observation (0008).** A single env's observation is a read-only numpy view straight onto the shared candle buffer, no copy, made sound by the candle's `repr(C)` layout.

**Compiled sweep, and why it is not in the Python API (0011).** `bar-engine` carries an in-core sweep that runs built-in Rust strategies over a parameter grid with the GIL released and no Python in the loop. It is deliberately not exposed to Python: it can only run strategies compiled into the engine, so as a public surface it would be one nobody could extend without writing Rust, which is a promise not worth making. Parameter search from Python goes through tuning instead, and the sweep survives in the crate as the benchmark of the GIL-free path.

**RL autoreset (0010).** The vector env uses same-step autoreset: a finished env's `step` returns the next episode's first observation, with the true final observation and equity in `infos`. The observation is a `(window, F)` window over a feature matrix you supply. On gymnasium versions that tag autoreset style, it declares `SAME_STEP` in its metadata so a vector wrapper does not assume the next-step default.

**Stable-Baselines3 adapter (0022).** SB3 will not take a gymnasium vector env; it wants its own `VecEnv`. `emsl.sb3.EmslVecEnv` presents the batched env as one, a straight remap because emsl's same-step autoreset already matches SB3's contract, so PPO and the rest train on the GIL-free batch with no re-vectorization.

**Per-env cost randomization (0014).** Each cost knob accepts a `(low, high)` pair sampled once per env, so a batch trains across a spread of cost regimes.

**The batched tier is market-order-only (0020).** The parallel RL and batch path takes only market orders; a per-order Python decoder cannot ride the GIL-free step, the same reasoning that refuses a per-fill cost function.

## Tuning

**Tuning over the Strategy spine (0021).** `emsl.tune` searches a strategy's parameters by running the same backtest across worker processes. It never serializes a live engine: it rebuilds one per worker from the candle array, carries the strategy and objective with cloudpickle, and lets optuna drive the search.

**A parallel search is not reproducible from the seed (0036).** With `n_jobs=1` a seeded search is exact: the same seed replays the same trials in the same order and returns the same winner. With `n_jobs>1` it is not, and cannot be. The driver asks for `n_jobs` trials before any result has come back, then asks for a replacement as each future completes, so the order results reach the sampler depends on which worker finishes first. The sampler sees a different history and suggests different points. Nothing is wrong; this is what asynchronous search is. But a seed that does not reproduce is exactly the kind of thing that costs an afternoon, so: pin `n_jobs=1` when a result has to be reproducible, and treat a parallel search as a search rather than a computation.

## Charting

**A series is aligned by position, and a short array draws late (0037).** A chart's arrays arrive as bare positional values with no index, because an index on a feature is a promise the library cannot check and a `reindex` is exactly where lookahead gets introduced. Length is therefore the only signal, and two lengths are honoured: a `T`-long array maps entry `i` to bar `i`, and a `T-1`-long array maps entry `i` to bar `i+1`. Any other length raises and names both numbers, because a silent trim or pad is a chart that is off by an amount nobody can see. The reason for the second case is not that `i+1` is the earliest bar such a value could be known, and it is worth being exact about this because the obvious wording is wrong: a number read off `state` inside `next` was known *on* bar `i`, and the right repair for one of those is to pad it to `T`. The reason is that drawing a short array early is the visual signature of lookahead, and that the engine records an equity point only on a real advance, so `equity_curve[i]` is the account at tick `i+1`. That is also what `numpy.diff` and `pct_change().dropna()` produce. Two arrays accumulated in one loop can legitimately want opposite treatments, so the guide gives both padding helpers by name rather than one rule.

**A NaN is a gap, never a dropped row (0038, corrected by 0073).** A value that does not exist is drawn as whitespace: the point carries a time and no value, and the line stops. The alternative, dropping the row, is what most plotting code does by default and it is a lie with a specific shape: the two neighbours become adjacent, and the renderer draws one straight segment across the hole, so a trailing stop that existed on bars 0 to 40 and again on bars 900 to 940 appears as a smooth line through 860 bars where there was no stop at all. Pine users know this distinction as `plot.style_linebr` against `plot()`, which joins across `na`. The rule holds for infinities too, since an infinity is a hole with a direction and there is nothing honest to draw at the top of an axis. The one concession to size is that a leading run of non-finite values, which is what a rolling window's warm-up is, is folded into the series' start offset rather than sent as nulls; that changes no pixel and keeps the alignment exact.

**A bare array overlays the candles unless it would flatten them (0039).** Passing an array with no panel is the most common call there is, so the layer has to guess. The obvious rule is range overlap: if the values fall near the price, draw them on the price panel. That rule carries no information about units, so an oscillator bounded 0 to 100 on a coin priced 20 to 90 overlaps, rides the candles, and stretches the price axis until the candles occupy a fifth of the panel they own. The rule is about harm instead: the array overlays when the merged axis still leaves the candles at least half the price panel, and gets its own panel otherwise. The threshold is not a tuning parameter, it is the guarantee, so the worst outcome the rule can produce is a series in a panel you would not have chosen, and the outcome it cannot produce is a price chart quietly crushed to make room for something else. It is a guess about the picture, never about intent, and `panel=` overrides it.

**The renderer is vendored into the wheel (0040).** The chart is drawn by TradingView's lightweight-charts, one 196 KB standalone JavaScript file under Apache 2.0, copied unmodified into `python/emsl/_static/` with its banner intact and the licence text beside it. It is not fetched from a CDN and it is not a `pip` dependency. A CDN link makes a saved chart stop working the day a path changes, makes a notebook useless on a plane, and leaves an offline research machine unable to open its own output; a pip dependency does not exist, because the artifact is JavaScript. The costs are named rather than hidden: the wheel grows by 196 KB, an upgrade is a deliberate file replacement rather than a version range, and a fix in the renderer needs an emsl release to reach anyone. The tests resolve the file out of the installed package rather than the source tree, because the gate copies only `tests/` and a packaging regression would otherwise surface at a user's first `save`.

**A chart is precomputed and self-contained, never served (0041).** Everything is computed once, in Python, before anything is drawn, and the result is one HTML document carrying its own renderer, its own styles and its own data. There is no server, no websocket, no build step, no bundler and no network call in the life of a chart. That buys three things worth more than live updating. A notebook cell's output is stored inside the `.ipynb`, so a chart survives being saved, emailed and reopened with no kernel behind it; a saved file opens by double click on a machine that has never had Python on it; and nothing can repaint, because there is no process left to repaint it. It is drawn inside an iframe with `srcdoc` rather than as raw HTML, because JupyterLab strips script tags out of raw HTML output while an iframe is its own document and always runs. The cost is size, roughly 260 KB of escaped renderer per cell plus the data, which is the price of a picture that still works in three years.

**The chart computes nothing and knows no indicator names (0042).** There is no `sma` in the shipped code, no `rsi`, no `zscore`, no indicator registry and no way to ask for one. Arrays arrive already computed and the layer turns them into marks. The reason is not minimalism, it is that a chart that computes can disagree with the run it is drawing: recompute a moving average outside the strategy and the picture is of a rule that was never executed, differing from the traded one by a warm-up convention or an off-by-one nobody will find. Passing `strategy.fast` draws the values the fills were decided on, so the line on screen cannot drift from the line that made the decision. It also keeps the dependency list at numpy, since every indicator library is somebody's opinion about warm-up and adjustment. The one derived number in the layer is the drawdown of the engine's own equity curve, which is a second view of a number the engine already returned rather than a statistic about your data. Even that one exception found the failure the rule exists to prevent: the curve records a point per advance, so the balance the run opened with is not its first entry, and a peak taken from the curve alone lost every fall from that balance. A first bar that lost money drew a flat zero panel directly under a headline reading the engine's own `max_drawdown_pct`. `BacktestResult` therefore carries `initial`, the panel is seeded from it exactly as the engine seeds its own, and both are capped at a total loss, because bad debt takes equity below zero and an uncapped fall reports a deeper bust as a larger number than a wipeout.

**The spec is the seam, and the bundle is an explicit list (0043).** Python and JavaScript meet at one JSON document and nowhere else: Python decides what is drawn and where, JavaScript decides only how it is painted. So the JavaScript holds no colours, no thresholds, no number formats and no arithmetic, and every one of those arrives as data, which is what makes them assertable from a Python test in a gate that has no browser. A grep of the shipped assets for a colour is part of that gate, and the only hit it allows is full transparency, which is a way of drawing nothing rather than a colour. The JavaScript itself is plain classic scripts concatenated inside one function at render time, from an ordered tuple written down in the module rather than from a directory glob, so a file that happens to land in `_static/` cannot join the shipped bundle. No file executes anything at load, which is what lets the same sources run as separate script tags during development and as one bundle in the wheel with identical behaviour, and it is why the development loop is edit-and-refresh with no npm and no build step anywhere in the project.

**Plotting is not declared inside a strategy (0044).** The natural instinct is a `Strategy.plot` hook where the arrays are computed, and it is deliberately not built. You change what you look at far more often than what you trade: a strategy's arrays are what drove its decisions, while a chart's list is usually a superset that adds a benchmark, a feature under evaluation, or the same indicator at a second parameter. Registering plots inside `init` would mean that adding one line to a chart requires editing the strategy and re-running the backtest, which puts friction exactly where this layer exists to remove it, and `init` runs on every trial of every sweep, so it would invite display-only indicators into the hot path of a 500-trial search. That last argument was measured rather than assumed, and it is right in kind and wrong in magnitude: a mark object costs a memcpy, about 0.02% of a trial, while what it invites in beside it does not, since `ramp` over 100k bars is 1.6 times an entire trial and a `Recorder` adds half again to the run. The correctness argument for the hook survives without it, because a strategy's arrays are already plain attributes and `Line(s.fast)` draws the values that were traded on; the organisational argument is served by an ordinary `marks()` method returning a list, which a sweep never calls, which names a window once so a legend cannot go stale, and which composes with marks added at the call site where a registry would not.

## Honesty

**A crossing limit pays the taker rate (0045).** Whether a fill is a maker or a taker was decided by the order's type, so every limit was booked as a maker regardless of where the market was when it filled. A limit already through the market at the bar's open is marketable: a real venue lifts it on arrival and charges the taker rate for it. On its own that is a rounding error in the fee line. Composed with two other things it was not. A maker rate is legally negative, because rebate tiers are real and the boundary explicitly allows one, and ADR 0006 accepts that a buy and a sell resting at the same price can both fill against a single wide bar, which is a bar-fidelity artifact rather than a mistake. Put the three together and a straddle of limits at one price came back flat and richer every bar, without bound, on both markets. Neither ingredient was a defect alone, and no test of either could have caught it; the test that does is the straddle itself, run at three maker rates on both markets, asserting the account never ends up ahead. The fill still prices at the limit and never better, which is a rule that had lived only in a docstring until this decision was written.

**A zero denominator ranks at infinity, not at zero (0046, extended by 0072).** Sharpe, Sortino and Calmar returned `0.0` when their denominator was zero, which reads as a safe neutral and is the opposite. A run whose equity never fell has no drawdown, so it scored a Calmar of zero, while the same run with a single 0.9% dip added scored 10.05: identical start, identical end, identical CAGR, and the one that lost money ranked infinitely higher. Sortino did the same to any run without a losing bar. This is precisely the argmax inversion ADR 0029 was written to prevent, surviving in the one branch its drawdown cap could not reach, and `profit_factor` three dozen lines below had been answering the identical question correctly the whole time by returning infinity. All four now share one rule: a positive reward earned against no measured risk is the best outcome there is and goes to the top; anything else stays at zero. ADR 0029 asks this set to be finite and monotone, and this is where those collide. Monotone wins, because the set exists to be ranked and a ranking that inverts is worse than a number that is large.

**The queue of pending market orders is bounded (0047).** The volume cap is per order (ADR 0005), and the queue those orders waited in had no limit at all, so one order split into a hundred took a hundred times the cap against a single bar while every slice was priced as though it were the only participant. `max_open_orders` had bounded the resting book alone. It now bounds both, which makes the evasion finite rather than honest: the real answer is a liquidity budget shared across a bar, and that changes results on every run that queues more than one order, so it is its own decision for its own release. `market_buy` and `market_sell` return an optional id as a consequence, which makes every order verb in the API agree about what a refusal looks like.

**The annualization is read from the candles (0048).** `periods_per_year` defaulted to 365 on a library whose own README asks the router for hourly bars. On a year of them that understates Sharpe by a factor of 4.9 and CAGR by 25, because the exponent reads a year of bars as 24 years, and with a non-zero risk-free rate it subtracts a daily rate from an hourly return and reports a negative Sharpe for a profitable strategy. Nothing said so. The candles already carry the answer, so `Backtester` and `tune` take the median gap between timestamps and derive it, and a tz-aware index is handled first rather than last because that is what an exchange feed actually produces. The median is what makes missing bars harmless: an outage inside a year of hourly candles leaves the typical gap at an hour, and an hour is what those candles are. It snaps to a real interval only when already within one percent of one, so a nearly regular feed reports 8760 rather than 8759.4, and a spacing matching no interval is reported rather than rounded, because a series typically five hours apart is a mixed or decimated feed and not four-hour candles. A numpy array carries no timestamps, so it warns and falls back rather than assuming. The result carries the annualization it was scored at, for the same reason it carries the opening balance: a second reading that has to infer it again is a second reading that can disagree.

**A tuned result is in-sample until it has been held out (0049).** Every trial fitted the whole series and `TuneResult.best_stats` was handed back with nothing marking it, in a library where the words in-sample, out-of-sample and overfit appeared in neither the README nor any of the seven documentation pages. That number is the maximum of a noisy score over every trial, so it is biased upward by the act of searching and by more the harder the search worked, and the README's own flagship example ran two hundred trials and printed it. No statistic computed from the same bars can undo that: a probability attached to an overfit winner is worse than no probability, because it reads as rigor. `oos=0.3` fits every trial on the first 70% and re-runs the winner on the last 30%, which no trial ever saw. The split is always the end of the series and never a random slice, because a strategy is a claim about what comes next and shuffling lets a trial fit around the very bars meant to test it. The winner warms up inside the held-out bars rather than being handed history across the boundary, which costs it the first few bars there and errs in the direction of understating the result. Leaving `oos` out warns, since a default this consequential cannot be silent without being a trap, and `oos=0` says you meant to search everything and passes quietly.

**A warm-up is declared, not guarded by hand (0050).** Every strategy in every example opened with `if i < self.slow: return`, and that line is doing more than skipping a few bars. Without it `self.closes[i - self.slow]` on an early bar is a negative index, which numpy resolves from the END of the array, so the rule reads prices from the far future, produces a spectacular result and raises nothing at all. It is the only place left in the library where a wrong answer arrives silently, and it was prevented only by the author remembering a line of boilerplate. `Strategy.warmup` is read once after `init`, so it can be computed from whatever `init` just looked at, and `next` is simply not called before it. The bars before it still advance and still fill whatever is resting, because a warm-up is a statement about when a decision can be made and not about when the market exists. The stronger fix considered was a price view that refuses a negative index outright, and it was rejected: a view that is not a numpy array stops behaving like one at the first piece of arithmetic, and the audience for this library is people who will write that arithmetic. The named views `closes`, `opens`, `highs`, `lows` and `volumes` ship as ordinary read-only strided views instead, which removes `data[:, 3]` from every example, and the remaining hazard is written down here rather than claimed closed.

**A result says what produced it (0051).** A `BacktestResult` carried its numbers and nothing about where they came from, which is fine for one run and useless by the twentieth. A notebook accumulates a great many of them, and the question that arrives in week two, whether Tuesday's 2.1 Sharpe was on the same bars and the same fees as today's 1.9, had no answer at all: the configuration lived only in the call that was scrolled off the top of the cell. It now carries the engine settings it ran under, an eight-character fingerprint of the candles it saw, the strategy's name and repr, and the library version. The fingerprint is computed once when the backtester is built rather than per run, so a sweep pays for it a single time, and it is deliberately short: the only question asked of it is whether two runs saw the same bars, and eight characters answer that in a printed row where sixty-four would not. `to_dict` leaves out the equity curve and the trade log, because neither distinguishes one run from another and both are large. This is the same argument that put `initial` and `periods_per_year` on the result, applied one level up: a number you cannot attribute is a number you will eventually misattribute.

**A liquidation cannot leave you owing money (0052, extended by 0067).** The forced close used to be priced at the bar's adverse extreme, which is the price the trigger was tested against and not the price the position was worth when its margin ran out. A long of 10 on 100 of margin, against a bar that wicked to 80, booked a loss of 200 and left the account owing 100. That is arithmetic, not an outcome: no venue hands a retail account a bill for twice its margin, and the number poisoned everything downstream, since a per-trade loss past -100% is not a thing a drawdown or a return can describe. A position cannot lose more than the margin behind it, so the exit is now priced where that margin runs out, and closing there leaves exactly nothing. Bad debt is not clamped away after the fact; it is structurally unreachable, which is the difference between a floor and a guarantee. The trigger is unchanged and deliberately so: there is no maintenance margin, so 10x means a 10% adverse move rather than the 9.5% a real venue would use, and this model therefore survives a band of moves that would have closed a live account. That is a known and accepted simplification of the bar tier. The liquidation fee is priced inside the exit rather than charged past it, which answers the obvious objection that there is nothing left to pay a fee with at the moment of ruin: the close lands far enough before that point for the fee to fit in what remains, so a real fee appears in the trade row and the account still ends at zero.

**The venue is one object, and it hands out the surfaces (0053).** The introduction claims one fill model sits behind a backtest, a search and an RL rollout, and until now that claim was upheld by whoever typed the eleven knobs typing them identically three times. Three call sites is three chances to disagree, and a search scored at one fee against a rollout trained at another is not a discrepancy anybody notices; it is a discrepancy that quietly answers a different question. `Market` carries them once. The shape it took matters more than the fact of it: the obvious design accepts a `Market` in the existing `market=` slot beside the ten other keywords, and that design cannot be made honest, because a keyword left at its default is indistinguishable from one passed at its default, so there is no way to tell an override from a silence without sentinel defaults across three signatures every documented example uses. Inverting it removes the question rather than answering it: the market hands out the surfaces, each method takes only the arguments that are not the venue, and a knob cannot be passed twice because there is nowhere to pass it. `replace` exists for the case the inversion would otherwise make awkward, comparing one venue against a dearer copy of itself. The keyword form is untouched and stays the right thing for a one-off.

**The deflated Sharpe needs a null it cannot supply itself (0054).** A search returns the best of many noisy scores, so its winner stands high partly because it is good and partly because it was chosen from a crowd. The deflated Sharpe corrects for that by asking what the best of that many looks would have reached by luck, and it needs two numbers to do it: how many independent looks were taken, and how far the scores scatter across them. Taking both from the search itself is the obvious implementation and it is wrong in a way that matters, because a TPE sampler concentrates its trials in the winning basin. Its trials are therefore not independent draws, and worse, the spread between them SHRINKS as the search converges, so the threshold falls exactly when the overfitting is worst and the number reads most reassuring precisely when it should not. That failure is silent and the output looks like rigor, which is worse than no output at all. So the null is a separate argument and a required one: a random search over the same space and the same bars, which is an honest best-of-N and cannot concentrate. Four things are refused rather than guessed, because each would make the answer describe a different question than the one asked: a null that is not a random search, a null over different bars (checked against the candle fingerprint rather than trusted), a search that selected on some other statistic, since the max-of-N logic applies to the quantity you selected on and not to whichever one you later fancy reading, and a null too small to have a spread. A failed trial still counts as a look, because a configuration you evaluated and rejected is one you looked at; counting only survivors would let a stricter activity floor lower the bar and make an overfit winner look better.

**Fourteen indicators, and the conventions written down (0055, extended by 0063).** An indicator module was resisted for a long time and the resistance was right in kind: an indicator library is mostly somebody's opinion about warm-up and smoothing, a hundred of those opinions is a hundred ways to disagree with the chart a reader already trusts, and every one of them becomes a compatibility obligation the day it ships. What changed the answer is that the alternative is not "no opinion", it is "your opinion, unwritten". A researcher hand-rolling an EMA picks a seeding rule without noticing there was a choice, and the curve that quietly differs from TradingView by a warm-up convention is exactly the failure ADR 0042 exists to prevent, one level further out. So the set is small and closed at fourteen, and every function states its own convention where implementations differ: `ema` seeds from the simple average of the first window rather than the first value, `rsi` and `atr` use Wilder's smoothing rather than the exponential one, `stdev` is population because that is what Bollinger bands are defined against. The alignment rule is the load-bearing one: one value per bar, warm-up as a gap, never a shorter array, so an indicator drops into a rule and into a chart with no padding decision between them and cannot invent a second convention beside the chart's own length contract. Nothing here touches the engine, and the chart still computes nothing: you compute once, trade on that array, and hand the same object to the chart, so the line on screen is the line that made the decision. Functions with more than one output return a named object rather than a tuple, because a caller unpacking three anonymous arrays in the right order is a caller who will one day unpack them in the wrong one.

**A wide bar books the worse exit (0056, corrected by 0071).** A bar whose range reaches both a stop-loss and a take-profit says nothing whatever about which it reached first, and the engine has to answer anyway. It used to answer with book-slot order, which is placement order, which is the order those two lines happen to appear in the strategy. The consequence was not subtle: place the stop before the target and every ambiguous bar books a loss, swap the two lines and every one books a win, on the same data and the same rule. A test written against this reports 90 in one ordering and 110 in the other. That makes the sign of a bracket strategy's result a property of how it was typed, which is the least defensible thing a simulator can do, and a bracket is the first pattern anybody writes. Exits from the same position are now applied worst first, ordered by the PnL each would realize against the open position, so the answer is a rule rather than an accident. Pessimism is the right direction for the same reason it is elsewhere in the engine: an optimistic guess about an unobservable ordering flatters a backtest, and a flattering backtest is the expensive kind of wrong. The ambiguity is rarer than it is important, since it needs a bar wide enough to span both legs, and those are exactly the bars carrying the outsized moves. The sort is stable and applies only to fills that reduce the position, so nothing else changes order, and a bar that reaches only one leg is untouched.

**A walk-forward is one run, not a stitching (0057).** The obvious way to build it is to backtest each window separately and glue the pieces together, and that way is wrong in three places at once. Each piece would open a fresh account, so a loss in one stretch would not shrink the size available in the next, which is the opposite of what refitting a live strategy does. Each piece would warm up inside its own bars, so a fifty-bar average would restart at every seam and throw away history that genuinely existed. And a position open at a boundary would have to be flattened, inventing a trade nobody placed. The curve that came out would then need its statistics computed by a second implementation, beside the engine's, which is the drift this codebase keeps paying for elsewhere. So the schedule of fitted parameters is carried by a composite strategy instead, and the whole walk-forward is a single ordinary engine pass: each bar is delegated to the window that owns it, the account is continuous across the seams, every warm-up sees the bars before its own window, and the result is a `BacktestResult` that every metric and the chart already know how to read. The cost is that the curve is flat until the first window, which is honest, since before that there was nothing fitted to trade. The boundary between a fit and the stretch it feeds belongs to the trading side, so no window is ever fitted on a bar it later trades. PBO by combinatorially symmetric cross-validation was considered as the alternative and rejected: it needs a matrix of per-trial returns that would have to cross the worker boundary, it recombines non-contiguous blocks by concatenating returns, which is unsound for a path-dependent engine whose positions and liquidations span blocks, it contradicts ADR 0049's rule that a split is always the end of the series, and it answers with a scalar against a soft threshold where this answers with a curve every existing tool already consumes.

**The deflation is about the search you ran (0058).** ADR 0054 separated the null from the study for a good reason and then read both halves of the threshold off the wrong one. The threshold is the sharpe the best of `N` draws spread `s` apart would reach by luck, and those two numbers come from two different places: `s` is a property of the space and the bars, which is exactly what an honest random search measures, while `N` is how many times *you* looked, which is a property of your search and of nothing else. `looks` was taken from the null. So a 120-trial search deflated against a 5-trial null was scored as though it had looked five times, and the same winner came back 46% more convincing than it did against a 400-trial null, with nothing in the output naming which search the number described. The count now comes from the study, every trial of it including the failed ones, and the null supplies only the spread. A null thinner than the search it judges still works and warns, since the spread is then estimated from fewer draws than the thing being judged. The second half is the same failure arriving through the other term: `spread` was computed from the null's *usable* trials, and an activity floor (ADR 0034) fails the thin cells, which are precisely where the extreme sharpes live, so the survivors of a floor scatter less than the space does. Measured on one search, turning on `min_trades=10` dropped the threshold from 2.74 to 1.98, which is the inversion ADR 0054 exists to prevent reappearing one term over. A null carrying an activity floor is now refused outright rather than corrected, because there is no honest way to recover the spread of trials that were never scored; the search being deflated may still use one, since a floor changes which winner you pick and not how far the space scatters. `TuneResult` carries `min_trades` for that check, for the same reason it already carried `sampler` and `data_hash`: a number computed about a search has to know which search it is talking about. The example shipped in the docstring and on the API page was wrong in a third way and would simply have raised, since it held out a tail in the study and not in the null, so the two ran on different bars and the fingerprint guard rejected the pair. It shipped because the documentation test parses examples and deliberately does not run them, which is its own finding and is answered in ADR 0066.

**A metric that takes a frame says which frame (0059).** Three functions in `emsl.metrics` take the candles beside the result, and none of them checked that the candles were the ones the result came from. `excursions` and `session_buckets` skipped any trade whose ticks fell outside the array, and `buy_and_hold` trimmed its two return series to a common length. All three then answered, plausibly, about something else. Given a 2,000-bar slice of its own 100,000-bar frame, `excursions` returned 35 rows out of 1,516 and said nothing at all. `buy_and_hold` was worse than short, it was misaligned: it trimmed the run's returns from the tail and the frame's from the head, so a `TuneResult.best_result` fitted on the first 70% of a series, benchmarked against the whole series, compared the run's last returns against the frame's first bars and reported a Sharpe 84% out and a beta out by a factor of ten. The chart refuses this class of mismatch in a paragraph, and the reasoning it gives, that a silent trim is a picture wrong by an amount nobody can see, is the same here. The guard is not the same for all three, which is the part worth writing down. `excursions` and `session_buckets` read the run's own tick indices straight into the frame's bars, so they need the *identical* series and check the candle fingerprint the result already carries (ADR 0051), which also catches the case a length check cannot: another asset of the same length made a losing trade report both of its excursions as gains. `buy_and_hold` needs only the same NUMBER of bars, because a different asset is not a mistake there, it is the entire point of a benchmark: `beta` and `information_ratio` are only interesting against something other than what you traded, and an identity guard would delete the one question in the library that can ask whether an ETH strategy beat holding BTC. Two smaller things travelled with this. `hold_sharpe` ignored `risk_free` while every other Sharpe in the library subtracts it, so the two printed side by side were different quantities. And `session_buckets(by="weekday")` numbered its days from Sunday, because epoch day zero is a Thursday and the offset was four rather than three, while `datetime.weekday`, pandas' `dayofweek` and every other clock a reader is holding number them from Monday. Nothing stated the convention, so `buckets[0]` read as Monday and was Sunday. It is now Monday-first and the docstring says so.

**A walk-forward window is scored on the run that happened (0060).** ADR 0057 refuses to build the curve by stitching per-window backtests, and then the per-window diagnostics beside it were built exactly that way: each window's out-of-sample score came from a fresh `Backtester` over that window's bars alone. Every objection in 0057 applies. The isolated run opens its own account, so a loss in one stretch does not shrink the next. It restarts every warm-up inside the window, so a winner whose warm-up is longer than the stretch it was chosen for never has `next` called at all, and the window reports a tidy `0.0` that is indistinguishable from a stretch which genuinely broke even. That is not a corner: with five windows over half a series, a stretch is a tenth of the data while the search is free to pick a two-hundred-bar average, and on one 1,200-bar layout two windows of four reported scores from runs that could not place an order. `decay` came out at 0.50 where the bars the composite run actually traded had earned 1.87, and `consistency` counted a window nobody traded as a window that failed to clear zero. The score is now read off the pass that happened, through `metrics.segment`, which restricts a finished result to a range of bars and computes the engine's own statistics over it, seeded from the balance the account carried into that range. That is a second implementation of arithmetic the engine already owns, which is the drift this codebase keeps paying for, so a test pins `segment` over the whole run against `result.stats` key by key. Two keys are deliberately absent from it, `exposure_pct` and `num_fills`, because a finished result does not carry what they are computed from and inventing them would be worse than omitting them. Each window also now reports `bars_traded`, the count of its bars its own winner could decide on once its warm-up is taken off, so a window that could not trade is visible as a window that could not trade rather than as a flat quarter. A callable objective returns `None` rather than a number, since a callable takes a whole result and a window is a slice of one; a number computed on a basis the caller did not ask for is the failure this decision exists to close, not a feature to preserve.

**Confidence is counted in bets, not in bars (0061).** `autocorrelation` was added to be read beside the probabilistic Sharpe, and its own docstring said what it meant: a strategy holding a position for two days on hourly candles has a few hundred independent bets rather than a few thousand, so every confidence figure computed from the bar count is overstated. Then `probabilistic_sharpe` and `min_track_record_length` both counted bars. The library diagnosed the problem in prose, printed the diagnostic beside the number, and declined to apply it, which is the worst of the three available positions: a reader who trusts the output is misled, and a reader who reads the docstring is told the output is wrong and given nothing to do about it. Both now count `effective_sample`, the standard `n (1 - r) / (1 + r)` for a persistent series at its first autocorrelation, and `min_track_record_length` converts its answer back into bars so the caller still gets the unit they asked in. `independent=True` restores the published formula for the case where the returns really are independent, which is rare here and is exactly why it is not the default: this library is pointed at hourly crypto and multi-day holds are the normal case, not the corner. Negative autocorrelation is floored away rather than credited, because the arithmetic would make the effective sample LARGER than the bar count and read as free confidence bought by mean reversion; the correction exists to remove overstatement and not to hand any back. `sharpe_interval` arrived with it, since the same estimator read as an interval rather than as a tail is usually the sentence somebody actually wants, and a lower bound at or below zero says the run does not distinguish itself from nothing however good the point estimate looks.

**The trade log gets a distribution, and the run gets a calendar (0062, extended by 0081).** The engine reported a win rate and a profit factor and nothing else about the shape of the trades, and those two are the same pair for a rule that grinds out small wins and for one that is short gamma waiting for the bar that ends it. A 70% win rate at a payoff of 0.3 is a losing rule; the rows to see that were already sitting in `result.trades` and nothing read them. `trade_stats` reads them: average win against average loss, the payoff between them, expectancy per trade, the largest of each, and the longest run of losers, which is what actually decides whether a rule gets switched off rather than whether it was profitable in the end. `summary` prints the win rate and the payoff on adjacent lines and will not print one without the other. Beside it, three absences that a single number cannot cover. `segment` restricts a finished run to a range of bars, seeded from the balance the account carried into that range so consecutive stretches compound to the whole, which `period_returns` uses to answer the first stability question anybody asks of a crypto backtest, whether the entire edge sits in one quarter, and which `rolling_sharpe` answers as a shape rather than a scalar. `decompose` gained `fee_share` and `turnover`, because "you have a cost problem rather than an idea problem" is a sentence neither the fee total nor the gross PnL says alone. And `report` gained `return_per_exposure`, since twenty percent made while in the market a twelfth of the time and twenty percent made fully invested were the same row.

**The indicator set grows by the families the library's own claims need (0063).** ADR 0055 closed the set at fourteen and the reasoning was right, but the closure had holes in exactly the places this library makes promises. `atr` says its purpose is deciding where a stop goes and `metrics.excursions` is sold as the direct answer to the same question, and there was no ATR band to put a stop on. Every documented example is a moving-average cross, whose textbook companion is a regime filter, and there was none. `to_ohlcv` explains at length that volume must be in base units because the fill model reads it, and no indicator let a strategy see whether a bar had any. So the set is 30: an ATR channel and a supertrend, ADX, a participation pair, the ordinary derived momentum readings, and a comparison group. That last group is the one that is about safety rather than convenience, and it is why this decision exists at all. ADR 0050 says the remaining hazard is a lookback deeper than the declared warm-up, where `values[i - n]` on an early bar is a negative index that numpy resolves from the end of the array and reads the future in silence, and it says outright that the hazard is written down rather than closed. `shift` closes the common shape of it: the array is padded rather than wrapped, and there is no index left to get wrong. `crossover` and `crossunder` remove the other one, since a cross written by hand is the most common place a strategy reaches back a bar at all. They are the only functions here that return booleans and pad with `False` rather than `NaN`, and that exception is load-bearing: `bool(nan)` is `True` in Python, so a float warm-up would fire a rule on precisely the bars where nothing is known. A crossing is a yes-or-no question and the honest answer during a warm-up is no.

**The recursive indicators are vectorized between their gaps (0064).** `_smooth` was a Python loop over every bar, and every recursive indicator went through it: 191 ms for one EMA over 100k candles against 18 ms for the simple average of the same length, 424 ms for RSI, 565 ms for MACD. Driven through a real backtest, two EMAs computed in `init` were 42% of an entire trial against 3% for two SMAs, and `init` runs on every trial of every search, so a 200-trial tune paid a minute of it. Each stretch between two gaps is a plain geometric decay, so the loop is now over the gaps and the stretches are one vectorized pass each. Two things are worth recording, because the obvious implementation is wrong and the correct one is not free. The one-line version writes the recurrence as a cumulative sum needing `(1 - alpha)**-k`, which overflows to infinity within a few thousand bars at any ordinary length and destroys most of the output silently: at length 20 over 100k bars it returns 7,045 finite values out of 99,981. The sum is therefore taken in blocks short enough to keep the largest weight well inside the float range, each seeded from the last value of the block before it, with the block size derived from `alpha` rather than picked. That size is computed by `ta._block` rather than inline, so a test can read the size the module actually uses: the three tests that cross a block seam used to recompute the formula beside themselves, which meant they agreed with their own copy of it, and replacing the module's with a picked 1000 left all three green while `ema(2)` returned silent NaN from bar 1001. And it is not bit-exact. Reassociating a sequential float64 recurrence cannot be, and the measured difference against the loop it replaces is at most 2.1e-15 relative, across every gap shape, both smoothing constants and every length tried. That is a deliberate trade rather than an accident: it is far below the precision any of these numbers are read at, no EMA crossover comparison changed on a 100k-bar series, and the alternative that preserves exactness is moving the recurrence into the Rust core, which would put an indicator behind the boundary ADR 0042 deliberately kept it outside of. The result is 33 times faster and the seeding rule, the gap rule and the warm-up are unchanged.

**What 1.0 promises, and what it does not (0065).** A version number is a claim about what may change under a reader without warning, and until it is written down the claim is whatever each person assumed. So: from 1.0, a minor release will not remove a name from `emsl.__all__`, remove a public function from `emsl.metrics`, `emsl.ta` or `emsl.plot`, remove a keyword from any of them, change what a keyword means, or change the type a function returns. New keywords arrive with defaults that keep the old behaviour, and new functions arrive freely. That is the ordinary part. The part worth stating explicitly is that **the simulator's behaviour is part of the API and not an implementation detail**. A backtest is a number somebody will act on, and a fill model that shifts quietly between patch releases makes every recorded result unattributable. The rules a reader may build on are: an order decided on bar `i` fills against bar `i + 1` and never the same bar; a `T`-bar series calls `next` `T - 1` times; a bar reaching both a stop and a target books the worse exit (ADR 0056); a liquidation is priced where the margin runs out so bad debt is unreachable rather than clamped (ADR 0052); the statistics are never `NaN` and rank monotonically (ADRs 0007, 0029, 0046); `emsl.ta` returns one value per bar with the warm-up as a gap and never a shorter array (ADR 0055); a `T-1` array drawn on a chart maps entry `i` to bar `i + 1` (ADR 0037); and `tune` holds out the END of a series and never a random slice (ADR 0049). Changing any of those is a MAJOR release, and it arrives with an ADR explaining what was wrong. What is deliberately NOT promised: the numeric output of an indicator to the last bit, since ADR 0064 already trades 2e-15 for a 33-fold speedup and that trade may be made again; the private surface, which is every name beginning with an underscore and every module beginning with one; the exact wording of an error or a warning; the chart's JSON spec, whose `schema` field exists to be bumped and which is never re-read by Python (ADR 0043); and the Rust crates, which are workspace members rather than a published API and carry no compatibility promise at all until one is written for them. The bar-tier fidelity limits (ADR 0006) are limits rather than promises: they may become MORE faithful in a minor release, since a simulator getting closer to a real venue is a fix, and results will move when they do.

**A documented example that composes two calls gets an executable test (0066, extended by 0078).** The documentation test parses every fenced example and checks that every keyword names a real parameter, and it says in its own docstring that it does not run them, because most stand on a frame and a strategy the surrounding prose describes. That is a reasonable line and it has a cost that came due: the flagship `deflated_sharpe` example, shipped identically in the docstring and on the API page, held out a tail in the study and not in the null, so the two ran on different bars and the function's own fingerprint guard rejected the pair. It had never been executed. Parsing cannot catch that, and no amount of parsing will, because the defect is in how two correct calls fit together. So an example whose point IS the composition of two calls gets a test that runs it against real data, rather than one that reads it. The general rule stays as it was, since an example that demonstrates one call is adequately covered by the signature check and forcing every prose snippet to be executable would make the pages worse.

**A liquidation is a price on the bar, not a check at the end of it (0067).** ADR 0052 says bad debt is structurally unreachable rather than clamped away, and that guarantee rested on something it never said: that the position was still open when the check ran. The check happened after the bar's fills, and `is_bust_at` needs a position to test, so an exit order that flattened the account first left nothing to liquidate and the loss was booked in full. A 10x long on 100 of margin against a bar that gapped open at 50 ended at **minus 400**, while the identical bars with no exit order ended at exactly zero. Placing a stop-loss made the outcome worse than placing nothing, which is the opposite of what a stop is for, and it is ordinary use rather than a corner. The same missing guard produced a second symptom through the other door: a partial close on the gap bar drove quote negative, and the closed form behind `bankruptcy_price` is derived assuming quote is positive, so with a negative one it solves to a price on the far side of the entry. The residual position was then "liquidated" at 120 on a bar whose high was 72, booking a profit of 80 and putting a liquidated winner in the trade log, which is a clamp wearing a price and precisely the thing ADR 0052 says this design is not. The repair is to stop treating the liquidation as an event at the end of the bar and treat it as what it is, a price on the bar's own path. The level is computed before any order is resolved, and the bar is clipped at it: a long sees nothing below it and a short nothing above. Everything past that price belongs to a market the account had already been closed out of, so an order that would have filled there simply never triggers, and a bar that OPENED past it killed the account before it opened, so the forced close happens first and nothing on that bar fills at all. The rule this buys is a price rule and not a timing one, which is what makes it decidable at bar granularity despite ADR 0006: coming down from the open the market reaches 95 before 90, so a stop at 95 genuinely saves the account and one at 60 genuinely cannot, and the engine now answers both the way the path does. The accepted approximation is that the level is read once, from the position carried into the bar, so a partial exit that improves it mid-bar is not credited within that bar; the error runs pessimistic, which is the direction the rest of the engine already errs in.

**A stop is consumed by filling, and only by what it filled (0068, extended by 0079).** ADR 0035 corrected the reading that a stop is spent the moment its trigger is crossed, and bound consumption to filling instead, so a bar that trades no volume leaves the protection armed. The code bound it to the fill model *offering* a fill rather than to a fill being *booked*, and those come apart in two places that matter. A cash or margin clamp can take an offered fill to nothing, so a breakout stop placed beside a market order that consumed the whole balance was deleted having traded nothing at all, which is the exact outcome ADR 0035 exists to prevent, reached through a clamp instead of through a dead feed. And consuming the whole order on any fill at all made a bar carrying a sliver of volume far more dangerous than a bar carrying none: on one crash, a bar with a thousandth of a unit filled that thousandth, threw the remaining protection away, and rode 9.999 of a 10-lot into the next bar, where a bar with exactly zero volume kept all of it and exited whole. A discontinuity that severe at a boundary nobody can see is not a fidelity limit, it is an accident. So a stop accumulates its fills and rests until it has none left, which is the rule limits have always followed, and the remainder stays armed for the next bar that can actually trade it. This costs the reading in ADR 0016 that a triggered stop is a market order and therefore IOC; a stop is protection, and the honest failure for protection is to persist rather than to evaporate.

**A refused replacement puts the original back (0069).** `replace` cancels the old order and then places the new one, and ADR 0032 defines its `None` as "nothing happened", which is the whole reason a trail written with it cannot leave two orders alive. Placement can be refused for reasons that have nothing to do with the id being gone: a non-finite trigger, a size at or below zero, a `post_only` limit that would now cross. In every one of those the cancel had already happened, so the method answered `None` having destroyed a live protective order. A caller doing exactly what the ADR tells them to do reads that as "the stop has already filled" and does not arm another, so the position is left naked by the one call written to make that impossible. The old order is therefore restored when the replacement is refused, into the slot the cancel just freed, which cannot itself fail, and it keeps its id so the caller's handle stays valid. `None` now means what it says on both paths.

**The boundary refuses what cannot trade, on both sides of the book (0070).** ADR 0027 hardened every argument crossing into the engine, and two gaps survived it, both found by asking what the risk clamps do with an input they cannot divide by. A candle price of zero or below is legal input, since the validator checks only for finiteness, and both clamps divide by the mark: the perp margin cap and the spot cash clamp each return without clamping anything when the mark is not positive, which is the one branch where the clamp is load-bearing. The fill behind them then bought an unbounded position for nothing, or for a credit. On spot, a buy of a thousand units against a bar priced at -100 *credited* the account 100,000 and took equity from 10,000 to 210,000; at a price of zero, a million units cost nothing and marked back to 100,010,000 on the next bar. `MAX_SLIP` exists so that a slipped fill can never reach zero, and the reasoning behind it, that a price at or below zero is not a trade, is now applied to the bar's own price as well. The second gap is that ADR 0047 made the pending market queue a bounded resource and it did not inherit the guard the resting book had carried since ADR 0027: a size that can never fill still took a slot, so two of them ahead of a real order refused it silently. `qty_from_weight` returns exactly zero on a flat mark or a dead account, which is how a strategy places one without meaning to.

**Only the exits reorder (0071).** ADR 0056 settled which of two competing exits a wide bar books and stated the limit of that rule in its own last sentence: the sort is stable and applies only to fills that reduce the position, so nothing else changes order. The implementation ranked a non-reducing fill at infinity and sorted the whole list, which moves every non-exit behind every exit. That is a different rule, and not a harmless one, because ADR 0006 says slot order is exactly what decides which of two fills gets the room when a cash or margin clamp binds on the first one applied. Hoisting the exits meant an entry could be funded by the proceeds of a sale that may just as well have happened after it: on a wide bar with a buy limit in slot 0 and a sell limit in slot 1, the account came out holding a full position and 170 of equity where slot order leaves it holding 0.56 and 165.56, and on a perp at its leverage cap the reordering admitted an entry that slot order refuses outright. The direction is the giveaway. Every version of this that ADR 0056 rejected was optimistic, and so was this one, so the sort was moving the optimism rather than removing it. The exits are now reordered among the slots the exits already occupy, and everything else stays where it was.

**A ratio that ranks losers must not reward the loss (0072).** ADR 0029 asked the statistics to stay finite and monotone and ADR 0046 fixed the branch where a zero denominator inverted the ranking; three ways the set could still mislead survived both, and all three matter because `tune` takes an argmax over them. Calmar divides a return by a drawdown, which on a losing run is a loss over a loss, so the deeper the bust the larger the divisor: a total wipeout scored -1.00 and a run that lost only 20% scored -3.71, and an argmax picked the wipeout. ADR 0029's own diagnosis, that the deeper bust gets the larger divisor and therefore the higher Calmar, was correct and its fix was a cap at 100%, which only equalizes busts against each other and leaves every pair below it inverted. A negative return is now scaled by its drawdown rather than divided by it, which is the identical number at a total loss, so the two branches meet, and it orders the whole losing half the right way round. Second, annualizing raises the growth ratio to one-over-the-years, and ADR 0048 derives that from the candles, so minute bars are ordinary input: 200 of them is 0.00038 of a year, the exponent leaves the float range, and a run ending +50% and one ending +300% both reported an infinite CAGR and an infinite Calmar, tied at the top of a sweep and borrowing the meaning ADR 0046 reserves for a reward earned against no measured risk. The value saturates instead of escaping, and the honest thing to add is that an annualized rate off a few hours is an extrapolation rather than a measurement, so `total_return_pct` is what to rank a sub-year run on. Third, `volatility_pct` is the only number here not routed through `ranked`, whose comparisons against a NaN are all false and fall through to zero, so a non-finite return surfaced as a NaN there and nowhere else; the returns are made finite at the source instead. What is deliberately NOT changed is Sharpe's treatment of a loser, where a larger deviation makes a negative excess less negative. That is the textbook ratio, everybody expects it, and a risk-adjusted return genuinely does say that losing steadily is worse per unit of risk than losing wildly.

**The renderer joins across whitespace, so a gap is a break between series (0073).** ADR 0038 is a claim about pixels: a value that does not exist is drawn as whitespace, the point carries a time and no value, and the line stops. Everything Python does is right, and a test asserts it, since the document carries a null for every missing bar. The renderer draws through them regardless. The proof needed a browser, which is why it took until one was in the gate: lightweight-charts 5.2.0, handed whitespace directly with none of this library's code in between, joins a line straight across it on both the line and the area series. So the failure ADR 0038 was written to prevent, a trailing stop that existed on bars 0 to 40 and again on 900 to 940 drawn as a smooth line through the 860 bars where there was no stop, was what the library actually drew, and the decision describing the alternative as the thing "most plotting code does by default" described itself. A break between two series is the only break the renderer honours, so a gapped track is drawn as one series per contiguous run. The split lives in the JavaScript rather than in the spec, and that is not a violation of ADR 0043's seam but an instance of it: the document was never wrong, one mark still means one entry in the legend and one line in the reader's head, and how many series it takes to paint that without lying is exactly the kind of question that side of the seam exists to answer. The cost is one renderer series per hole, which is why the leading warm-up run is still folded into the offset rather than left as nulls.

**A taker price never leaves the bar that produced it (0074).** ADR 0067 made bad debt unreachable through the liquidation, and then a property test over random walks found it reachable anyway, from outside the liquidation entirely. Market impact is `impact` times the fraction of the bar's volume a fill takes (ADR 0013), and the total slip is bounded only by ADR 0024's `MAX_SLIP`, which is a rule about not reaching zero rather than a rule about the market. The volume cap (ADR 0005) permits an order to take a whole bar, so the fraction reaches one, and at a coefficient of 0.5 a buy was priced 50% above anything that bar traded near: on one generated case, a fill at 133.56 against a bar whose entire range was a single price of 89.04. Nothing about that is a fidelity limit. A venue cannot fill outside what traded, and the loss booked against a price the bar does not show is bounded by nothing at all, which is why it walked straight through a guarantee derived from the bar. So a taker price is held inside the bar's own range, a buy at the high and a sell at the low. This subsumes `MAX_SLIP` rather than sitting beside it, since a bar that traded is a bar whose prices are positive, and it costs one thing worth naming: on a bar that printed a single price, slippage is now zero, because a bar that traded at one price is a bar where that is the price you got. It is a bound rather than a change of behaviour, and an ordinary slip off the open is untouched by it. The finding is also the argument for the method: this defect was invisible to reading, invisible to every point test written for ADR 0067, and took one property over random walks to surface.

**A panel with nothing to scale by draws nothing, which is the worst way to be wrong (0075).** Every primitive converts a price through a series, and a series carrying only whitespace has no first value, so the renderer skips it before it ever asks for a range and every conversion off it comes back null. The anchor is exactly such a series: an invisible line covering every bar with no values on it, there so a pane exists in panel order before anything is drawn on it. Three things were hanging off it. A `Level` was attached to whichever line or histogram reached its panel first, and the candles were never a candidate, so `emsl.chart(frame, Level(110.0))`, about the simplest call on the page, drew no level at all; the comment above that code shows the authors hit this exact failure once and fixed it one case short, because `frameFor` had already learned to prefer the candles and the level path had its own list that had not. A `Band` or a `Marker` alone on its own panel mounted cleanly, threw nothing and painted nothing, since a panel drawn entirely by primitives has no series with values on it by construction. And `Panel(range=)` was silently ignored on any such panel, for the same reason: the provider that pins an axis is only consulted for a source the scale did not skip. The level now hangs on `frameFor`, which subsumes the list it replaces and adds the candles, and a panel with no value-carrying series seeds its anchor with the extent of whatever is drawn on it, which is free because the anchor is transparent. The general lesson is worth more than the three fixes: a chart that throws is a chart you debug, and a chart that silently omits one mark is a chart you believe. Every one of these passed the whole suite, because the suite asserted the document and the document was right.

**The legend cannot report a colour the chart did not paint (0076).** The legend prints a swatch in the colour the series *is* at the hovered bar, and that promise is the reason a multi-coloured line is readable at all. It was breakable in two ways and both were live. A `Line` given both a per-bar ramp and a `fill` becomes an area, and an area carries one `lineColor` and ignores a per-point colour entirely, so the line was painted flat while the swatch went on reporting a different colour every bar; neither half can be preferred without lying about the other, so the pair is refused at construction, which is the same "refusing beats lying" the rest of the library runs on. The second is subtler and is really a hole in ADR 0043. A ramped series passed `color: undefined` to the renderer on the reasoning that the per-point colours would supply it, and `undefined` is not the absence of an opinion, it is the vendored bundle's opinion: its option merge skips an undefined key, so lightweight-charts' own `#2196f3` survived, and a bar the ramp left uncoloured was painted library blue while the legend reported it grey. The asset grep that ADR 0043 relies on cannot see that, because the literal is in the bundle rather than in ours, so the rule was being enforced on the file and not on the picture. Both now pass an explicit colour from the theme. Travelling with them, the overflow guard: the legend wrapped and counted a remainder as `+N`, and the test that decided whether an entry fit was skipped for the first entry on a line, so an entry wider than the pane was painted and clipped by the canvas with no counter, and the counter itself was drawn with no width check and could be clipped off the right edge. A legend that quietly drops a series is the one thing this block exists to prevent, and it was producing it.

**A control nobody clicks is a control nobody knows is broken (0077).** Three defects found by writing the browser tests rather than by reading, which is the point worth recording. The per-panel A / L / % buttons sit at the bottom of their band, and that is exactly where the renderer puts its own draggable pane separator, at `z-index: 50` against their 4. On a two-pane chart they work, so every hand check passed; on anything with more panes below the price panel they are covered and a click does nothing, and the flagship call, a frame plus a run, has four panes. Nothing had ever clicked one: the tests asserted the controls existed and carried the right names, which is the shape of coverage that feels thorough and touches nothing. Second, the trade log's chart-to-row direction keyed each bar to one trade, and the later assignment won, so a rule that is always in the market, where one trade exits on the bar the next enters, made every exit bar unreachable; the first claim on a bar now wins, and the exits are claimed first, because an exit is what you are looking at when you ask what just happened. Third, `Marker(offset=)` is documented as a distance in pixels and was multiplied by the interface scale, so a stated 16 landed anywhere between 13 and 21 depending on the size of the cell and the same call framed differently in a notebook and in a saved file. Everything else in that primitive still scales, because a glyph and its type should grow with the chart; the offset is the one number the caller wrote down and it is now honoured literally.

**The page with the most examples gets a prelude and runs all of them (0078).** ADR 0066 drew the line at composition: an example whose point is how two calls fit together earns an executable test, and one that demonstrates a single call is adequately covered by the signature check. That line has now cost two flagship examples, and the second one shows what was wrong with it. The plotting guide's longest block read `run.label` off a `BacktestResult`, which has never had such an attribute, so it raised on the first copy-paste; parsing cannot see an attribute, only a keyword. Beside it, a hand-rolled crossover compared two pandas slices, which align on their index rather than by position and produce a different array of a different length, and a forward return did the same and failed silently rather than raising, so the block whose entire purpose was a warning about padding shipped the wrong array. None of those is a composition of two calls. All three are a single call standing on a value the prose described and nobody had ever built. So the page gets a prelude, bound the way the page binds its own names at the point it binds them, and every block that stands on it is executed with `show()` and `save()` swapped for `spec()`, which builds the whole document and raises everything a real call raises. The cost is a fixture to keep in step with the prose, and it is worth paying here because this page carries forty examples and a reader copies them rather than reading them. The general rule is unchanged for the other pages: this is the page where the density made the trade obvious, not a new policy for every snippet in the doc set.

**An order retires at the epsilon it can no longer fill at (0079).** The engine held two different answers to "is this order finished" in two different places. A fill is refused when its size falls at or below the dust epsilon, which is ADR 0023's rule and is applied everywhere a size is booked. A resting order was retired only when its remaining reached exactly zero. An order whose remaining lands between those two thresholds can never fill again, because the clamp zeroes it, and never expires, because the retire gate never fires: it holds a slot in the book for the rest of the run. It costs nothing to produce. Ten fills of `0.1` against a size of `1.0` leave `1.1e-16` behind, and every partially filled order that ends on a float residue rather than on a clean zero leaves another. With `max_open_orders` at its shipped default of eight, a strategy resting orders over a long series accumulates them until the book is full, and from that point ADR 0028 makes every further placement a silent rejection: `None` comes back, the strategy carries on, and the equity curve simply goes flat. The natural reading of that curve is that the signal stopped firing, not that the simulator ran out of room, which is what makes it the expensive kind of wrong. ADR 0027, extended by 0070, had already condemned exactly this shape of failure and named exactly this harm, reaching it through a non-finite price rather than through an exhausted one, so the rule was written down and the second gate simply did not inherit it. Both gates are now the dust epsilon. The wider lesson is the one worth keeping: ADR 0068 says a stop "rests until it has none left" and never said what none means, and a threshold left unstated in the prose is a threshold two pieces of code will eventually disagree about. This is also the first defect found by running an independent simulator, written from this page alone, against the engine over random paths; it surfaced as five separate disagreements in three thousand cases that all reduced to this one line, and no test written against the implementation would have asked the question.

**A short period is still a period (0081).** `period_returns` skipped any calendar period holding fewer than two bars, which reads as tidying away a degenerate statistic and is a hole in the one thing the function promises. ADR 0062 puts it plainly: the periods are computed on the equity the account carried into each of them so that they compound back to the whole run, and a monthly table that does not multiply back to the headline it sits under is worse than no table. A year of hourly candles ending a bar or two into a month is not a corner, it is the ordinary shape of real data, and those bars vanished: `sum(bars)` came up short and the product missed the last stretch's return, silently and in the direction nobody checks. The guard appeared in no docstring and in no decision, which is what let it survive: it looked like housekeeping. A one-bar month reads oddly on the page and a missing one reads as arithmetic, so the odd-looking answer is the honest one. This was found by an adversarial pass over a test written the same day to pin exactly this claim, which had asserted the identity against a fixture whose three months were all long: the test was right about what to check and wrong about what to check it on, and the defect sat between them.

**Funding is marked on the bar the account was actually in (0082).** ADR 0067 clips the candle at the price a position's margin runs out at, and every order on that bar is resolved against the clipped one: `fenced` describes itself as the honest picture of a market the account was not in. Funding was the one event that reached past it, marking the position at the raw close. So a short liquidated on a bar that went on rising was credited funding for the whole rise, at a price it had already been closed out of. On the case that found this the engine credited 38.76 where the account only existed up to 107.386, overstating the credit by 13%, and the number is reported: `funding_paid` is wrong on any run with a liquidation in it. Worse at the margin, funding is charged BEFORE the liquidation check on purpose, so that a funding debit can bust the account on the bar it happens; a credit computed past the fence runs the same machinery backwards and can hand the account enough to clear a bust check it had already failed, which is ADR 0067's own guarantee defeated from outside it, exactly as market impact defeated it in ADR 0074. Funding now marks at the resolving bar's close, which is the raw close whenever there is no fence and the fence itself when the bar ran past it. Found by the batched differential, and only there: the single-engine harness compared position and equity, and a liquidation zeroes the equity on both sides, so 3,000 cases over six seeds could not see it. Both harnesses now compare `funding_paid` too.
**A refused replacement keeps its place in the queue (0083).** ADR 0032 defines a `None` from `replace` as nothing having happened, and ADR 0069 puts the original order back so that is true of the book as well as of the caller. It was not true of the order's PRIORITY. The restore went through `place`, which takes the first free slot (ADR 0006), so an order whose neighbour had been cancelled was silently promoted up the queue by a replacement the book had refused. Resolution follows slot order, and slot order decides who gets the room when a clamp binds: on a spot book holding 60 of cash against a limit at 40 and a limit at 50, the one resolved first fills whole and the other takes what is left, so the promotion moved the position from 1.4 to 1.25. Nothing in the engine or the reference had ever exercised it, and the comment beside the restore asserted the opposite in as many words, that "the slot the cancel just freed is the one being reclaimed", which the book does not promise and does not do whenever an earlier slot is free. The book grew `cancel_at` and `restore` so the engine can put an order back where it was rather than where the next placement would go. The successful path is unchanged and still takes the first free slot, because a replacement that succeeded is a new order and ADR 0006 is exactly the rule for one. Found by the differential the day a `replace` action was added to it, which is also the day ADR 0032's side-carrying stopped being asserted nowhere.

**A documentation picture is built from data that cannot move (0085).** Fourteen chart images ship with the documentation, and twelve of them were already drawn from a frozen parquet, which is what makes a documented example and the picture beneath it unable to drift apart. The two whole charts were not. They pulled a year of hourly candles from the router at the moment they happened to be run, so the picture on the front page of the README was the one nobody could reproduce and the one nearly everybody sees: re-running it did not regenerate it, it drew a different year, which means it could never be checked against anything and a defect in it could only ever be found by eye. Both now read the same published five-minute dataset, and the generator lives in `dev/charts` rather than in a scratch folder beside the repository (ADR 0084). The evidence that the move cost nothing is that thirteen of the fourteen images came back byte for byte identical to the ones already committed, including the projection chart, which was rewritten from a notebook into a function on the way; the fourteenth is the one that had been live. The trap found doing it is worth recording, because it is silent. The chart asks for `system-ui, -apple-system, "Segoe UI", sans-serif` and a container has none of the first three, so every label in every image is drawn by whatever that particular box resolves `sans-serif` to. The browser image resolves it to a CJK face whose latin glyphs are narrower and lighter, so the first run re-rendered the entire documentation set in a font nobody chose, and the only reason it was caught is that twelve images which should have been identical each came out three percent smaller. A picture is a test result like any other: if a rerun cannot produce it again, it is not evidence of anything.

**A per-env cost is an argument like any other (0086).** ADR 0027 says every argument crossing into the engine gets the same treatment, and for the four per-env cost arrays that was false. `build_config` validated the scalars, and the arrays went through a separate path that checked contiguity and length and nothing else, so they were the one way past every range guard in the boundary. `emsl.Batch(data, num_envs=2, fee_taker_per_env=[-2.0, -2.0])` was accepted where `fee_taker=-2.0` is refused, and on a perp four buys of five units took equity from 10,000 to 14,000: a rebate larger than the notional, minted out of a fill that cost nothing. The reinforcement learning surface reached it in the ordinary way rather than by contriving an array, because ADR 0014's `(low, high)` range hands `build_config` only the high end, on the reasoning that the expensive end is the safe thing to fall back to; a range straddling the floor therefore passed the guard on 0.0 and handed the negative draws to the unchecked array, so `VectorEnv(fee_taker=(-2.0, 0.0))` built happily and paid its envs to trade. Slippage and impact were accepted the same way and did no damage, because the fill model floors both at zero when it prices a taker (ADR 0004), which is defence in depth working exactly as intended and is also why nothing noticed for so long: three of the four holes were harmless and the fourth was not. The rule now lives in one function per kind and both paths call it, since a rule written twice is a rule two paths will eventually disagree about, which is the whole of what happened here. The range is checked in Python as well, on its lowest end, so the message names the range the caller typed rather than the array element it drew. Found by re-measuring the coverage audit rather than by a test, and worth recording for that reason: the claim had read as covered because a test asserted the scalars, and the arrays were a second path nobody had thought to point the same question at.

**Every picture in the documentation is produced by something committed here (0087).** ADR 0085 said a picture a rerun cannot produce is not evidence of anything, and settled it for the fourteen chart images while leaving the five hand-made diagrams half done: one had its mermaid source in the repository and four existed as PNG alone, their originals never kept. Half a rule is worse than none, because it reads as a rule and is not one, and the four that could not be regenerated were exactly the four nobody would notice going stale, since a diagram of the crate layering does not fail a test when a crate moves. All five now have a `.mmd` beside them and one stage renders the set, the same shape the chart images already had. The four reconstructions were read back off their own PNGs, so a rerun redraws them rather than reproducing them, and the honest check on that is 205314: it is the one whose source survived, and it still renders byte for byte identical through the rebuilt pipeline, which is what distinguishes a pipeline that is faithful from one that merely runs. The reconstruction also turned up the reason the palette has to name more colours than it appears to need. Mermaid derives whatever a partial theme leaves out, and the derivation drew the no-lookahead diagram's bar frames as opaque brown boxes behind the nodes; the committed image had been correct for as long as nobody re-rendered it, which is the failure mode this decision exists to remove.

**A page may only point at something that ships (0088).** ADR 0085 settled that a picture a rerun cannot produce is not evidence, and ADR 0087 extended it to the diagrams; this is the same defect one step further out, and 1.0.0 was tagged with it. The plotting page closed its hardest section, the one on a forward return being padded at the wrong end, by offering the notebook where that comparison was actually printed, and the notebook lived in the scratch folder the charting layer was built in rather than in the repository. The link read `../../`, which from a page one level down is already past the root, so it was broken for every reader from the moment it was published and could only ever have worked on the one machine it was written on. A test for exactly this existed and passed, because it followed `.md` targets alone: the pages link to each other constantly and that was the case worth catching, so the pattern was written to the case rather than to the rule, and the single link that was not a page was the single link that was wrong. The check is now on any target, and it asks whether the path leaves the repository rather than whether it resolves, because the gate lays the pages out flat under `/docs` while a checkout keeps them under `.Documentation`, so resolution needs a different answer in each and depth needs none: one level up is the root in both. What it does not catch is a link that stays inside the tree and names a file that is not a page and is not there, which is the narrower version of the same mistake and wants a real resolution to find. The scratch folder is gone, which is the other half of the fix, since a reference to something outside the repository is only ever repairable by deleting it or committing what it points at.

**A golden records what the code does, not what it was meant to do (0089).** `Marker` and `Markers` are one primitive drawn by one file, and the plotting page says so twice: `Marker` takes a single colour, and `Markers` takes the same keywords as `Marker`. Both constructors validated and stored `text` and `color` identically. Only the plural branch of the spec builder wrote them out, so a single `Marker` carrying a label and a colour drew an unlabelled glyph in the theme accent, and nothing raised, because `callout.js` gates the label on the key being present and falls back to the accent when the colour is not. The interesting part is not the omission, it is why five hundred tests did not see it. `everything()`, the fixture whose entire job is to put one of every mark on one chart so the key-path golden covers the union, contains a `Marker` written with `text="here"` specifically to cover this. The key never appeared, `dev/golden.py` recorded the key set it actually found, and the golden then pinned the absence as the contract for every commit after. A golden is a photograph, not a specification, and it is worth exactly as much as the fixture that fed it: it will faithfully hold a bug in place if the bug was present the day it was taken. The fix is four lines and the guard against a repeat is not another golden but an assertion that the two branches agree, since the defect was always a difference between two things that are supposed to be the same.

**A number computed about a search knows which direction it searched (0090).** ADR 0058 said this about the objective and the sampler, and three places had it only half done. `walk_forward` takes `direction`, validates it, hands it to each window's study and then drops it, so `WalkForward` never received it and its two diagnostics assumed higher is better. Under `minimize` the decay inverted outright, reporting a comfortable positive number for the windows that improved and a negative one for the windows that fell apart, which is worse than no number because the docstring tells the reader that a large positive means the search is finding things that do not survive. Consistency was worse still, and in a way a sign flip does not repair: it counts the share of windows that cleared zero, and a minimized objective is a magnitude that is positive whenever it exists, so `max_drawdown_pct` pinned it at exactly 1.0 and read as a flawless procedure while meaning every stretch drew down at all. The decay is now turned over under `minimize` so positive always means degraded, and consistency refuses rather than answering, because zero is a break-even for a maximized score and nothing whatsoever for a minimized one, and the file already prefers `None` to a number computed on the wrong basis (ADR 0060). `TuneResult` now carries the direction too, for the same reason and with a second victim: the deflation asks how high the best of many looks would reach on luck alone, so handing it a deliberately minimized winner compares a number against the opposite end of the spread it was drawn from, and it answered anyway because it could only see the objective. It now refuses. The tests that existed asserted the decay was a float and the consistency was between zero and one, both of which the broken path satisfied perfectly, which is the shape of a test written against a type instead of a meaning.

**A run that ended at zero says so (0091).** ADR 0031 added `num_fills` because a run that never filled was indistinguishable from one that traded, and the same principle had not reached the other end. A forced close books an ordinary trade row carrying `liquidated`, which is correct and is what ADR 0052 arranged, but two surfaces dropped it and one case never had it. The chart's trade payload is an explicit key list and `liquidated` was not on it, so the row that consumed the account rendered as an ordinary exit and a reader could reasonably blame a bad rule rather than their own leverage. Worse, `is_bust` and a liquidated row are not the same condition: the engine calls an account bust whenever equity reaches zero at a close on either market, and a spot account or a flat perp drained by fees and funding gets there without a forced close and therefore without booking any row at all, so that run carried no trace whatsoever. `BacktestResult` now carries `bust` and reports it in `to_dict`, and the chart marks the forced close in the trade table. Deliberately not a stat: `Stats` is a float dict that `tune` takes an argmax over, a liquidated run already ranks last on a total return of exactly -100, and adding a key there is a permanent commitment for something the trade log and the new flag both already say.

**A sweep names the strategy it cannot build (0092).** `cost_curve` and `breakeven_bps` rebuild the strategy for each run, so a class handed to them has to be constructible with no arguments, and every example in the documentation defined its tunables as constructor arguments and then passed the class. The examples raised on the first line a reader would copy, in the README and in the API page, and they raised with Python's own message about missing positional arguments, which names neither the sweep nor the fix. The examples now pass a configured instance, which is what the sentence directly beneath one of them already said the API intended, and the rebuild path catches the failure and says which class could not be built and what to pass instead, the same courtesy `_own_the_fees` had been extending one function away for as long as it has existed. The documentation tests could not have caught this and still cannot in general: they parse every block and check that every keyword names a real parameter, and here the call was two positionals against a signature that takes two positionals. The defect was in a value, and a value only fails when something runs it.

**A number that saturates has to saturate on both sides of the boundary (0093).** ADR 0072 made the growth rate saturate rather than escape, because on minute candles the exponent leaves the float range and an infinity there means something ADR 0046 has already reserved. The Python mirror of that arithmetic carried the ceiling and could not reach it. `(final / opening) ** (ppy / n_returns)` on Python floats RAISES `OverflowError` where the `f64` it is copying returns an infinity, so `min(cagr, _CAGR_CEILING)` on the very next line was dead code in exactly the case it was written for, and the mirror of a decision about very large exponents was the one place that could not survive one. ADR 0081 is what turned it from a minute-bar corner into an ordinary crash: it deliberately keeps a one-bar calendar period rather than dropping it, on the grounds that a year of hourly candles ending a bar into the next month is the shape of real data, and a one-bar period puts the whole annualization in the exponent, 8760 on hourly bars. So `period_returns` died on hourly candles, `segment` and `walk_forward` on minute ones, while `result.stats` beside them reported the saturated number correctly, which is the tell that the two halves had diverged. Fixed at the source rather than by widening the `except` in walk-forward's scorer: that one catches `ValueError` to mean a window cannot be scored, and widening it to any exception would convert a defect anywhere beneath it into a window silently missing from the average, which is the failure the whole file exists to detect. The reason it was never seen is worth recording, because it is a general trap: the suite runs everything at 365 or 8760, so a decision made about minute bars had no test at minute-bar annualization, and a ceiling nobody could reach looked exactly like a ceiling nobody needed.

**The margin bounds the fill, not the bar (0094).** ADR 0067 moved the liquidation check ahead of the fills and clipped the candle at the fence, and it accepted one approximation in writing: the level is read once, from the position carried into the bar, so a partial exit that improves it mid-bar is not credited within that bar, and the error was said to run pessimistic. It does not, in three shapes, and all three end with the account owing money that ADR 0052 calls structurally unreachable and ADR 0065 froze into the 1.0 API. A position GROWN during the bar is bounded by a fence computed for a smaller one, and an account that entered the bar FLAT carries no fence at all, so a market entry and a protective stop armed in one decision, which is exactly what the guide teaches, booked the whole distance: on a bar wicking to 55 at ten times leverage the run reported -400.96 percent against -100.00 for the identical bars with no stop, so placing the stop was four times worse than placing nothing, which is ADR 0067's own headline symptom returned by a different door. A resting limit prices at its own limit and never passes through the taker clamp that ADR 0074 added, so it walked out from underneath the fenced candle its trigger had respected, exiting at 20 on a bar that traded 50 to 60 with the fence at 54.6. And a partial exit that drove the quote negative left a residual position for the forced close to price off a balance the closed form at `bankruptcy_price` assumes is positive, which solves to a price on the far side of the entry: a liquidation booked at 102.48 on a bar whose high was 101, a profit of 9.09 on a dead account, and a run reporting a 50 percent win rate and a lifted profit factor behind a tidy -100 percent return. That last one is the dangerous one, because the first two are loud and pessimistic while this one flatters and every number it prints still looks plausible. The bound is now read at the moment a fill lands rather than a step earlier, and it applies to any fill that reduces a perp: closing at the bankruptcy price leaves equity exactly zero AT that price, so a partial close is bounded by the same number as a full one and no ordering of fills within a bar can book past it. ADR 0045 is untouched, because the bound exists only where the margin has run out: a gap take-profit on a healthy account still fills at the limit and never better, and a test pins that an exit asked for at 99 still happens at 99. The cost is a floating-point residue, since a fill bounded exactly at the margin point leaves something like 8e-13 on an account of 1000 rather than a clean zero, so such a run is flat and functionally dead, every further order refused as dust, while `state.equity <= 0.0` does not fire and the bust flag stays false; widening that comparison was rejected because ADR 0019's terminal is what the reinforcement-learning surface reads, and a defect in the accounting is not worth loosening a termination rule to paper over. The reason none of this was caught is the part worth keeping: the property test that says there is no fourth shape drove market orders alone, one per bar, so no run it ever generated had an order still resting when the bar resolved, and every one of these three needs one. Widened to arm a protective stop in the same decision as the entry, it finds the defect at tick 1.

**An excursion is a bound, and it counts only the part of a bar the trade was in (0095).** The worst and best a trade went were read from the entry bar's high and low through to the exit bar's, whole at both ends, and a trade is not in either of those bars whole. The exit bar is the one the closing fill resolved on, so everything it printed afterwards belonged to nobody and was folded in anyway; the engine already disagreed, since `bars_held` is `exit_tick` minus `entry_tick`, one fewer bar than the span being read, which makes it an internal inconsistency rather than a judgement call. The entry end was worse, because it is wrong only for the orders that flatter. A market entry fills at its bar's open and genuinely did live through that bar, but a resting limit fills partway through, and a maker bid rests BELOW the market so the bar has to come down to it and everything it printed on the way is ABOVE the entry: on a hand case where the bar opened at its own high of 130, fell to a bid at 100 and never printed above 101 again, the most a target could have caught was one percent and this reported thirty. On an ordinary maker-bid strategy over four thousand bars it inflated the favourable excursion on twenty three of seventy one trades, by as much as 1.5 points against a mean of 2.4. The rule now is the only one bar data supports: a bar prints its open first and its close last and nothing else in it is ordered, so the entry bar is known from the fill forward to its close, the exit bar from its open up to the fill, and the bars strictly between were lived through whole. That makes both numbers a bound that never overstates, which is the useful direction for the question being asked, since a lower bound on the adverse move says a stop needs to be at least this wide. The cost is real and is stated in the docstring rather than hidden: a market entry did live through its whole entry bar and does not get credited for it, because nothing in a trade row records which kind of order opened the position, and adding that field would mean a new column on every trade for a post-hoc diagnostic, on a position that may have been scaled into by several fills of different kinds, so a single flag would be an approximation of its own.

**The four prices have to be a bar (0096).** ADR 0027 says every argument crossing into the engine gets the same treatment, and ADR 0070 went back over the candle array a second time for a non-positive price, but neither asked whether the four prices were in any order at all: the boundary checked five columns, at least one row, and finiteness, and nothing else. That matters because of what ADR 0074 built on the assumption. The taker clamp bounds a fill to what the bar traded by taking the smaller of the price and the high on a buy, and the larger of the price and the low on a sell, which is a bound only while the high is above the low; on a row where they are not, the same min and max move the fill TOWARD the account instead of away from it, silently, with no warning and always favourably. The reachable cause is not a typo. Coinbase Exchange returns its candles as time, low, high, open, close, volume, so slicing columns one through five positionally out of that feed produces an array in which the high is at or above the low on EVERY row and every value is finite, and four hundred bars of alternating buys and sells on a market whose every open and close is exactly 100 return a full percent at zero fees and zero slippage. That case is also the argument for checking the whole ordering rather than the obvious pair, because a high against low comparison passes it untouched and would have read as a fix. The boundary now requires the low to be at or below the open and the close and the high to be at or above both, in the loop that was already walking every bar for finiteness, so it costs one comparison per row on a buffer that has just been copied. The message names the column order, since the two realistic ways to arrive here are a positional stack with the high and low transposed and a feed that ships them the other way round, and both are one line to fix once someone says which it is. The rule is inclusive at both ends, so a bar that never moved is still a bar and a dead feed is not refused as malformed.

**A reference draws after the thing it is a reference to (0097).** ADR 0075 found a `Level` hanging on a carrier only the line and histogram branches ever filled, so the simplest call on the plotting page drew nothing, and it moved the level onto the panel's own frame so the candles could carry it. That fixed the price panel and left one hole, because the engine's two panels get their series later: the equity and drawdown curves are pushed in after the level loop has already run, so a `Level` on either found nothing to scale by, fell through to the whitespace anchor, and painted not one pixel. The plotting page documents marks on the equity panel as a supported composition, and a line across an equity curve at the balance the run opened with is close to the first thing anyone draws there. Measured in a browser, a magenta level counted 3173 pixels on the price panel, 3052 on a panel that happened to have a line, and exactly 0 on equity and on drawdown. The loop now runs after both curves are added rather than before, which is a move of six lines and no new mechanism. Two render tests pin it, and the reason they are render tests rather than spec tests is the shape of the defect: the document was always correct and the mark was always in it, so nothing readable from Python could tell the difference and only counting painted pixels can. Worth recording beside them is how the drawdown one first failed, because it failed honestly: the level was placed at -5.0 on a panel whose worst fall was -0.087, and a reference outside the range it is drawn on paints nothing either. A test can fail for the defect it names and for something else entirely, and the two are indistinguishable until the fixture is made to sit inside its own panel, which is why that one now takes its value from the run's own worst fall.
